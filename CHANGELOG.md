# Release Notes

## [Unreleased](https://github.com/Refactor-Circus/Guardian/compare/v0.1.0...main)

Guardian v2.0.0 is the suite's security package: a JSON API and MCP tools, with no PHP UI; it ships its Atrium front-end module.

### Breaking

- The Atrium UI is gone: the Atrium plugin, its pages and views, and the `ui` and `atrium` config sections are removed, and Guardian no longer registers with Atrium. Atrium v2, or any front end, uses the JSON API (`openapi.json`, `@refactor-circus/guardian-client`) and MCP.
- Requires `refactor-circus/keystone` `^2.0`; works with `refactor-circus/roster` `^2.0` (for SSO and SCIM) and `refactor-circus/keen` `^2.0`. Guardian requires no other suite package.
- Guardian is the suite's role store: with `authorization.bind` on (the default) it binds Keystone's `Permissions` and `Roles` and registers a `Gate::before`, so every package's permission checks are answered from Guardian's role tables. Roster v2 no longer stores roles; Roster's `roster.roles.*` permissions become `guardian.roles.*`.
- SSO and SCIM check their abilities through Keystone's contract and assign the default member role through Keystone's `Roles`.
- New tables: roles and permissions, security events, two-factor (methods, recovery codes, passkeys, one-time codes, policies), devices, sessions, password histories and IP rules, all named through `tables`. Set `users.key_type` (`int`, `ulid` or `uuid`) before migrating when your users' keys are not integers.

### Added

- Roles and permissions, moved from Roster: `GuardianPermissions` and `GuardianRoles` (scope chains, owned roles, super roles, configured `super_admins`, a request memo and an optional cache), the escalation guard, the `guardian.roles.*`, `guardian.permissions.*`, `guardian.role-assignments.*` and `guardian.users.abilities.index` routes and their MCP tools, `php artisan guardian:sync-permissions` and `php artisan guardian:grant-super-admin {email}`.
- `php artisan guardian:adopt-roster-roles` and the `adopt_roster_role_tables` migration: copy Roster v0.1's role tables into Guardian's once, keeping every ULID and every user's answers.
- Abilities `guardian.roles.view`, `guardian.roles.manage`, `guardian.roles.assign`, `guardian.two-factor.manage`, `guardian.sessions.manage`, `guardian.tokens.manage`, `guardian.security.view` and `guardian.security.manage`.
- A security log (`guardian.security-events.*`, `guardian.me.security-events.index`) of sign-ins, failures, lockouts, sign-outs, password, two-factor, session, token and IP events, with identifiers stored only as HMACs and no secrets; pruned after `security_log.retention_days`.
- Two-factor authentication: TOTP, email and SMS codes through the `OneTimeCodeChannel` contract (mail by default), passkeys with `web-auth/webauthn-lib`, recovery codes, the sign-in challenge, the `guardian.two-factor` middleware, two-factor policies by role and scope with grace days, and the `TwoFactorRequirement` contract.
- Sessions and devices: the `guardian.session` middleware, session and device lists, signing out one or every other session (optionally with API tokens), admin revocation, and a new-device notification.
- A password policy: `PasswordPolicy::rules()`, breach screening through HIBP's range API, password history, the `guardian.password-fresh` middleware, and the `password-policy` and `passwords/check` routes.
- API tokens through the `TokenDriver` contract, with Sanctum and Passport drivers (`tokens.driver`): list, issue (HTTP only) and revoke, with ability and lifetime limits.
- Login protection: the `guardian.login-throttle` middleware (lockouts by identifier and address), clearing lockouts, suspicious sign-in alerts, and IP allow and deny rules enforced by the `guardian.ip` middleware.
- `openapi.json`, the OpenAPI 3.1 document of the API, and `@refactor-circus/guardian-client` 2.0.0 (`createGuardianClient`), regenerated by `composer client:generate`.
- Ships its Atrium module: Guardian's Atrium front end (pages and screen tabs) as a prebuilt JavaScript module in `dist/atrium/`, declared in composer.json's `extra.atrium` and injected by Atrium v2 into its page. Guardian declares its Atrium integration (nav, screens, hook tabs and section) in a manifest, `dist/atrium/integration.json`. No Composer dependency on Atrium.
- Config sections `authorization`, `users`, `roles`, `super_admins`, `permission_cache`, `adopt`, `security_log`, `two_factor`, `sessions`, `devices`, `passwords`, `tokens`, `login` and `ip_rules`.

### Upgrading to v2.0.0

1. **Atrium.** Remove any Atrium v1 wiring of Guardian's pages and the published `guardian.php` `ui` / `atrium` keys; use Atrium v2, which reads Guardian's API.
2. **Dependencies.** Require `refactor-circus/keystone` `^2.0`, `refactor-circus/guardian` `^2.0` and, for SSO and SCIM, Roster v2 (`refactor-circus/roster` `^2.0`), together: `composer require refactor-circus/guardian:^2.0 refactor-circus/roster:^2.0 refactor-circus/keystone:^2.0`.
3. **Config.** Re-publish or merge `config/guardian.php` for the new sections. If you map Roster's organization or team models to morph aliases, set `adopt.scope_types` to those aliases before migrating.
4. **Migrate.** Run `php artisan migrate`. It creates Guardian's new tables and adopts Roster's roles: while Guardian holds only its seeded built-in roles, `roster_permissions`, `roster_roles`, `roster_permission_role` and `roster_role_assignments` are copied into Guardian's tables, with organization and team scopes, owned roles and `roster.roles.*` / `roster.sso.*` / `roster.scim.manage` permissions mapped to Guardian's.
5. **Check the adoption report.** The migration writes it to your log; `php artisan guardian:adopt-roster-roles` prints it again (it reports "already adopted" after the first run, and "nothing to adopt" without Roster's tables). Check that your users hold the roles you expect.
6. **Drop Roster's role tables by hand** once you are satisfied: Guardian never alters or drops the four `roster_*` role tables.
7. **Wire the middleware** you want (`guardian.login-throttle`, `guardian.two-factor`, `guardian.session`, `guardian.password-fresh`, `guardian.ip`) and, for API tokens, set `tokens.driver`. See the README's Host wiring.


## [v0.1.0](https://github.com/Refactor-Circus/Guardian/commits/v0.1.0) - 2026-10-30

### Added

- SSO (OIDC, SAML, Microsoft Entra ID) and SCIM 2.0 provisioning, moved from refactor-circus/roster with their behaviour unchanged: HTTP API, ten MCP tools, `guardian.*` permissions and Keen auditing as package `guardian`.
- `php artisan guardian:upgrade-from-roster` and the `2026_11_01_000000` upgrade migration: rename Roster's SSO and SCIM tables and permissions to Guardian's, keeping rows and grants, once Roster has handed SSO and SCIM over. Leftover `roster.sso.*` / `roster.scim.*` config is listed.
- Stranded-data warning on `php artisan about` and a reported exception per boot.
- Create-migration rollback refuses to drop tables with rows unless `GUARDIAN_FORCE_ROLLBACK=true`; each migration checks only the tables it drops.

### Changed

- Changed from Roster: OIDC sign-in links an existing account by email, or creates one just in time, only when the id_token's `email_verified` claim is `true`. Otherwise the sign-in is refused (reason `unverified_email`). Identities already linked, SAML and Microsoft Entra ID are unchanged.
