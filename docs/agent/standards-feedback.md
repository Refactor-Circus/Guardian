# Standards Feedback

Every time work has to break a standard, add a row. `/ring-master-discover-standards` reads this log, so changes to the shared standards are based on evidence.

| Date | Spec | Standard | Deviation | Why |
| --- | --- | --- | --- | --- |
| 2026-10-30 | 2026-10-29-2038-guardian-package | models/migrations | The create migrations (`2026_11_01_000001` / `000002`) skip each `Schema::create()` whose table already exists, and their `down()` throws `RollbackRefusedException` (a `GuardianException`), dropping nothing, while any of the tables that migration drops holds rows (D-040), unless `guardian.migrations.force_rollback` is on. | The upgrade from Roster renames Roster's SSO/SCIM tables into place before these run, so a plain create would fail and a plain `down()` would delete an install's connections, identities and tokens (spec criterion 21, D-031). |
| 2026-10-30 | 2026-10-29-2038-guardian-package | architecture/dependencies | `src/Upgrade` (`Handover`, `RosterUpgrade`) names Roster's SSO connection class, its `roster_*` SSO/SCIM table names, its `roster.sso.*` / `roster.scim.*` permission names and config keys, and its `permissions` / `permission_role` tables as strings, and writes those tables with the query builder rather than through Roster's models or actions. | The upgrade path is about Roster by definition: it must detect whether Roster still ships SSO without loading the class, and move data Roster no longer has models or actions for (spec Design, criterion 22). |
| 2026-10-30 | 2026-10-29-2038-guardian-package | architecture/service-providers | `GuardianServiceProvider::register()` registers `Domains\DomainServiceProvider` from an `$this->app->booting()` callback, not directly in `register()`. | Without a Roster that has the seams, Guardian must register no domain providers (criterion 7, D-023, D-032). The gate is `Support\Integration::rosterInstalled()`, a singleton tests and apps can rebind; asking it while providers still register would resolve it before such a binding exists. `booting()` runs before any provider boots, so the domain providers still boot with the rest. |
| 2026-10-30 | 2026-10-29-2038-guardian-package | architecture/dependencies | `Domains\Sso\Concerns\JoinsOrganizations` (used by `SsoLoginAction` and `ScimUsers`) writes Roster's `MembershipModel` and `RoleAssignmentModel` directly (membership with a source, then the default member role) rather than through a Roster action. | Roster's join lives in its `Domains\Organization\Concerns\ManagesMemberships` trait, outside the public API Guardian may use (criterion 9), and its only public joining action, `AddMemberAction`, always uses the `direct` source and refuses an existing member, so SSO (`domain`) and SCIM (`scim`) could not keep their behaviour through it. The rule is copied as is; a Roster action that joins with a registered source would remove it. |
| 2026-10-30 | 2026-10-29-2038-guardian-package | http/resources | `Domains\Sso\Resources\UserSummaryResource` is a second serializer for the user, beside Roster's `Domains\User\Resources\UserSummaryResource`, nested in `SsoIdentityResource`. | Roster's resource is part of its HTTP layer, which criterion 9 forbids Guardian to use. `tests/Feature/Sso/UserSummaryResourceTest.php` holds the schema and payload equal to Roster's, so the two cannot drift unnoticed. |
| 2026-10-30 | 2026-10-29-2038-guardian-package | actions/actions-events | Read actions (`List*`, `ShowSsoConnectionAction`) dispatch starting/finished events, which the standard says read actions skip. | Keystone's `Arch::actionEventGaps()` requires the pair on every action, and Roster's moved actions did the same (D-041). |
